# CityLife 技术全景与源码导读

> 目的：把项目中的技术点放回具体业务请求里理解。此文档基于 2026-10-07 的 CityLife 工作区代码、[原项目公开介绍](https://javaup.chat/hmdp-plus/overview/project-intro/)、[原仓库 README](https://github.com/java-up-up/hmdp-plus)和用户提供的简历参考内容。原站部分技术正文需会员权限，本文件不是那些受限文章的复制或替代全文。**代码存在 ≠ 功能已完成全部故障验证 ≠ 你亲自开发。**

## 0. 一张架构图

```text
Vue 页面
   |
Spring MVC Controller -- 登录信息 / 参数校验 / 入口限流 / 访问令牌
   |
业务 Service ---------- Redis: 缓存、Lua、集合、限流、追踪
   |                     Redisson: 锁、延迟队列、布隆过滤器
   +---- Kafka Producer -> Kafka -> Consumer -> MySQL / 对账日志
   |                                      |
   +---- ShardingSphere-JDBC -------------+-> 多库多表
```

这是**调用关系的简化图**，不是所有功能都经过每个组件。先看 [README](../README.md) 运行方式，再从 Controller 沿一次请求向下跟；公共框架仅在调用到它时再进入。

## 2. 先看四条业务链

### 2.1 登录：请求如何知道「我是谁」

[UserController](../citylife-core-service/src/main/java/com/citylife/controller/UserController.java) 接收手机号/验证码；[UserServiceImpl](../citylife-core-service/src/main/java/com/citylife/service/impl/UserServiceImpl.java) 把验证码短期存 Redis，登录成功生成令牌，并将用户信息放入 Redis。后续请求由拦截器读取令牌、查 Redis、填充当前线程的用户信息。这里的登录令牌，与秒杀访问令牌、令牌桶的抽象令牌是**三种不同概念**。当前“发送验证码”代码记录日志，不能自动理解为已接真实短信网关。

**要会说**：请求携带什么、Redis 存什么、拦截器把用户数据放到哪里、请求结束如何清理线程上下文。

### 2.2 查商户：缓存穿透和击穿发生在哪

[ShopServiceImpl#queryById](../citylife-core-service/src/main/java/com/citylife/service/impl/ShopServiceImpl.java) 当前走 V4：Redis 命中直接返回；未命中先过布隆过滤器、空值键；接着加 Redisson 锁并做第二次缓存检查，只有仍然未命中才查数据库并回填。不存在的 ID 走负缓存，减少反复查库。`CacheClient` 另有直通、互斥锁和逻辑过期写法，但 V1/V2/V3 不是此接口当前路径。

**要会说**：穿透是查询不存在的数据；击穿是热点键失效后许多请求同时查库；雪崩是大量键集中失效。三者不能混答。

### 2.3 秒杀：项目的主线

```text
获取访问令牌 -> IP/用户限流 -> 下单接口再次限流 -> 一次性令牌校验/删除
-> 查询券与用户等级 -> 雪花 ID -> Redis Lua 检查并预扣
-> Kafka 异步发送 -> 接口返回订单 ID
-> 消费者校验延迟 -> DB 条件扣库存 -> 写订单/路由/对账日志 -> 手动确认消息
```

入口在 [VoucherOrderController](../citylife-core-service/src/main/java/com/citylife/controller/VoucherOrderController.java)；当前业务路径是 [VoucherOrderServiceImpl#doSeckillVoucherV2](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)，而不是保留的 V1。Redis 脚本在 [seckillVoucher.lua](../citylife-core-service/src/main/resources/lua/seckillVoucher.lua)，消费者在 [SeckillVoucherConsumer](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)。返回 ID 仅说明走到异步发送位置，**不代表 Kafka 已确认，更不代表数据库订单已提交**。

**要会说**：请求线程和消费线程各做了什么；库存有 Redis 预扣和 DB 最终扣减两份；失败会出现哪几种不一致状态。

### 2.4 取消和候补：库存回流后去哪里

[VoucherOrderServiceImpl#cancel](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java) 更新订单状态、恢复 DB 库存、写恢复对账记录，并尝试清理 Redis 预扣状态。随后从订阅 ZSet 找最早的未购且合格用户，调用秒杀 Lua 及 Kafka 尝试自动分配。[VoucherServiceImpl#subscribe](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java) 保存订阅用户与订阅时间。这个流程跨 MySQL、Redis、Kafka，不能把一个 `@Transactional` 理解为对三套系统同时回滚。

## 4. Redis 数据结构与数据怎样变化

| Key 模式（按券 ID 等拼接） | 类型 | 写入/删除时机 | 作用 |
| --- | --- | --- | --- |
| `seckill:access:token:{券ID}:用户ID` | String | 签发时写，验证成功或 TTL 到期删除 | 一次性请求凭证 |
| `seckill:limit:ip:tb:{券ID}:IP`、`...user:tb...` | Hash | 每次限流计算更新 `tokens/last_ms` | 令牌桶状态 |
| `seckill:limit:ip:sw:{券ID}:IP`、`...user:sw...` | ZSet | 请求时追加、移除窗口外记录 | 滑窗状态 |
| `seckill:stock:{券ID}` | String | 加载 DB 库存、Lua `INCRBY -1`；回滚删缓存 | Redis 预扣库存 |
| `seckill:user:{券ID}` | Set | Lua `SADD`，回滚时可能 `SREM` | 一人一单预校验 |
| `seckill:trace:log:{券ID}` | Hash | 预扣/恢复时写追踪，随后对账读 | 追踪变更与差异定位 |
| `seckill:voucher:{券ID}` | 序列化对象 | 查 DB 后写，更新券时失效 | 秒杀券 L2 缓存 |
| `seckill:subscribe:zset:{券ID}` | ZSet | 订阅时按时间入队，分配/取消时调整 | 候补时间顺序 |
| `seckill:shop:topbuyers:daily:{店铺ID}:日期` | ZSet | 下单成功加 1，取消减 1 | 每日购买**次数**榜 |

这些键来自 [RedisKeyManage](../citylife-redis-tool-framework/citylife-redis-framework/src/main/java/com/citylife/core/RedisKeyManage.java)。花括号里的券 ID 是 Redis Cluster Hash Tag，使同一券的脚本多键尽量落在同一槽；不是 Java 模板语法。

### Lua 秒杀的最小例子

```text
初始：stock=1，purchased={}
用户 A：检查时间/状态 -> stock > 0 -> A 不在 Set -> stock=0，Set={A}，写 trace -> 返回成功
用户 B：stock=0 -> 返回库存不足；Set 和 trace 不变
用户 A 再来：可能先因 stock=0 被拒；这份脚本先查库存、后查已购集合
```

最后一行是阅读代码时容易遗漏的细节：**失败码取决于检查顺序**，不能想当然说第二次一定返回「重复购买」。Redis Lua 只保证脚本执行期间不被其他 Redis 命令穿插；它既不包 Kafka/DB，也不是自动回滚的数据库事务。

### 令牌桶的最小例子

容量 3、3 秒补满，补充速率即每秒 1。第 0 秒连续 4 次，前 3 次通过、第 4 次被限；第 1 秒补回 1 枚，可再通过一次。当前 [tokenBucket.lua](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/resources/lua/tokenBucket.lua) 使用 Redis 时间，计算 `min(capacity, oldTokens + delta * rate)`。同一脚本先检查 IP 再检查用户，若 IP 已扣令牌而用户被拒，IP 令牌不会自动退回；这是阅读实现时应意识到的计数语义。

## 5. 一致性：按故障位置分开讨论

| 故障/差异 | 当前代码可见的处理 | 仍要验证或补足 |
| --- | --- | --- |
| Redis 脚本拒绝 | 请求在 Kafka 之前失败，不生成 DB 订单 | 返回码、前端提示是否对应 |
| Redis 预扣成功，Kafka 主下单发送失败 | [主下单生产者](../citylife-core-service/src/main/java/com/citylife/kafka/producer/SeckillVoucherProducer.java)异步失败回调尝试 Redis 回滚 | 业务未等待 Future；未找到主下单 Outbox，回调前宕机等窗口可能留下预扣痕迹 |
| Kafka 发送成功，消费延迟超过阈值 | 消费者放弃下单并尝试回滚，记录对账日志 | 回滚失败与重放时序需要实测 |
| 消费执行时 DB 库存不足/订单重复/其他异常 | 方法标注 `@Transactional`，消费失败路径尝试 Redis 回滚 | 跨分片数据库事务的原子性需核对事务模式；Redis 回滚不是 MySQL 事务的一部分 |
| 消息重复消费 | UUID 锁限制并发、已有订单检查、条件库存更新 | 注解默认无成功标记；顺序重放与数据库约束需测试，不等于严格 exactly-once |
| DB 有订单、Redis 追踪丢失 | 对账服务可回填追踪并删除库存缓存重建 | 当前未找到自动定时触发 |
| Redis 有扣减追踪、DB 无订单 | 对账服务可删库存缓存、清理相关标记 | 只覆盖仍能扫描到的追踪；TTL、Redis 故障可能导致信息缺失 |
| 券配置更新，其他实例 L1 仍旧 | 发布 Kafka 失效消息，其他实例消费清缓存 | 消息延迟/失败窗口，需做多实例故障测试 |

这里的「补偿」往往是**删 Redis 库存缓存并从数据库重建**，并不总是 `INCR 1`。[回滚 Lua](../citylife-core-service/src/main/resources/lua/seckillVoucherRollBack.lua) 在库存键不存在时直接返回错误，失败路径也需要观察。

## 6. 分片、ID、锁、事务：四个容易混在一起的边界

1. **分片**决定数据落在哪个库和表。当前 `tb_voucher_order` 用用户 ID 选库、券 ID 选表；`tb_voucher_order_router` 用订单 ID 路由。查询条件缺分片键可能广播。[规则文件](../citylife-core-service/src/main/resources/shardingsphere.yaml)
2. **雪花 ID**给不同记录生成 ID，不负责查询路由。当前 41 位时间、5 位数据中心、5 位工作节点、12 位序列；实例编号分配与时钟稳定是唯一性前提。[生成器](../citylife-id-generator-framework/src/main/java/com/citylife/toolkit/SnowflakeIdGenerator.java)
3. **锁**限制对同一券/商户的并发进入顺序，数据库 `stock > 0` 条件更新进一步防止库存负数。锁不会让 Redis/Kafka 自动参与数据库事务。[券更新](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)
4. **事务**为被事务管理器覆盖的数据库操作提供提交/回滚边界；涉及不同分片时，是否跨库原子还取决于 ShardingSphere 事务模式，当前配置未见明确 XA 声明。跨 Redis + Kafka + MySQL 仍要状态记录和补偿；`@Transactional` 不能替代消息发送确认。[订单创建](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)

## 7. 业务扩展的真实边界

- **订阅与候补**：Set 表示订阅成员，ZSet 保存订阅时间；库存回流后尝试最早候补。[VoucherServiceImpl](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)
- **开抢提醒**：延迟队列触发选人、去重和日志通知；短信/App 开关默认关闭，不是已接第三方短信。[ConsumerDelayedVoucherReminder](../citylife-core-service/src/main/java/com/citylife/delay/consumer/ConsumerDelayedVoucherReminder.java)
- **每日 Top 买家**：订单消费者按店铺/日期给用户 ZSet 分数加 1，取消则减 1；当前是订单次数，不是消费金额。[SeckillVoucherConsumer](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)
- **取消**：更新 DB 状态、恢复 DB 库存、处理 Redis 状态并尝试候补。跨系统中间态应单独考虑，不能说一步事务覆盖全部。[VoucherOrderServiceImpl](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)
- **运营库存修改**：有写锁、DB 与 Redis 更新和增量候补尝试；未看到原文所说的版本号乐观校验，不应照搬。[VoucherServiceImpl](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)

## 8. 原文亮点与当前代码的差异

用户提供的简历参考是**写法素材**，不是当前代码的验收报告。以下项目先保持「待实现/待验证」标签：

| 原文常见说法 | 当前代码核对结果 |
| --- | --- |
| 「令牌桶 + 滑动窗口串行兜底」 | 配置二选一，默认令牌桶 |
| 「主下单发送确认、指数退避、DLQ、本地消息表全链路」 | Kafka 配置有确认/重试；主下单失败回调尝试 Redis 回滚；明确的指数退避/DLQ 主要在**缓存失效消息**，未找到主下单 Outbox |
| 「定时自动对账、自愈所有故障」 | 有对账方法和手动接口，未找到周期调度；各类宕机仍需故障注入 |
| 「全站 L1+L2 + 逻辑过期异步重建」 | 券信息走 L1+L2；商户当前 V4 不走逻辑过期 V3 |
| 「K8s Worker ID 动态注册回收，绝对不重复」 | Redis Lua 分配编号并在上限回绕；未见租约机制 |
| 「订单超时自动关闭释放库存」 | 找到开抢提醒延迟队列，未找到自动关单完整链路 |
| 「Top 买家按消费金额、真实短信触达」 | 当前 ZSet 分数为购买次数；提醒通知默认主要记录日志 |
| 「百万并发、P95/P99 优化了 XX%」 | 没有可引用的固定环境压测对照数据 |

这些差异不是否定项目价值，而是帮助你把**已有代码、设计意图、待补功能和实测成果**分开。这样面试追问时才能稳。

## 9. 推荐学习与验证路线

1. **业务和数据**：看登录、券、订单 3 个 Controller/Service，画出用户、券、订单主键关系。参考[原站表结构目录](https://javaup.chat/hmdp-plus/basics/db-relations/)；以当前 `sql/` 与分片规则为准。
2. **Lua**：把 `seckillVoucher.lua` 每个返回码列成「前置条件、Redis 哪些键变化」。重点验证并发库存为 1 和同用户重复请求。
3. **限流**：手算令牌桶 4 次请求与滑窗 4 次请求，再读 Lua；把访问令牌与限流令牌分清。
4. **异步订单**：从 V2 的 `sendPayload` 追到 Consumer、订单/路由/对账三张表；亲自回答「什么时候订单才算成功」。参考[公开异步秒杀概览](https://javaup.chat/hmdp-plus/coupon-flash-sale/async-reliability-refactor/)。
5. **缓存**：用不存在的商户 ID 与热门商户 ID 各模拟一次，跟踪布隆、空值键、锁和 DB；再单独看券的 Caffeine L1 及失效消息。
6. **分片与 ID**：在 `shardingsphere.yaml` 为具体订单算出库表；手算两次雪花 ID 的差别。参考[公开 ID 文章](https://javaup.chat/hmdp-plus/components/distributed-id/)。
7. **故障演练**：分别停 Kafka、延迟消费者、清 Redis 某个键，记录接口返回、Redis 键、DB 订单和日志；不要先写「最终一致」，要观察实际能否恢复。
8. **简历筛选**：看[候选要点](简历候选要点.md)和[面试问答](面试追问与回答.md)，只保留你能用代码、运行结果和个人改动证明的 4-5 条。

每学一项都用同一模板复述：**问题是什么 -> 数据起初在哪里 -> 代码按什么顺序改变数据 -> 失败时留下什么状态 -> 如何验证**。这比背完整原站资料更有用。
