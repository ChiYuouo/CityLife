CityLife｜本地生活服务平台

技术栈： Java 17、Spring Boot 3、MyBatis-Plus、MySQL、ShardingSphere-JDBC、Redis、Lua、Redisson、Kafka、Caffeine

项目介绍： 面向商户查询、探店与优惠券抢购场景，围绕高并发秒杀、热点数据访问和异步订单处理，构建涵盖入口控制、库存预扣、订单落库及异常补偿的业务链路。

项目亮点：

搭建优惠券抢购入口控制链路，组合 IP/用户维度的 Redis 限流与 30 秒一次性访问令牌，在进入库存处理前完成频率控制和凭证校验。

将活动时间、券状态、库存和一人一单校验收敛到 Redis Lua 脚本中，完成原子预扣及扣减流水记录；串联 Kafka 异步落库，并在发送失败、消费超时和异常路径尝试回滚，保留数据供后续对账。

构建秒杀券信息的 Caffeine + Redis 两级缓存，通过消息通知各实例清理本地缓存；商户查询结合布隆过滤器、空值缓存和加锁后二次检查，控制无效查询与缓存失效时的并发回源。

落地 ShardingSphere 订单 2 库 4 表路由，按用户 ID 选库、券 ID 选表；结合雪花 ID 和订单路由记录，处理跨分片订单标识与查询定位。

扩展售罄订阅与库存回流流程，使用 Redis ZSet 维护订阅顺序，在取消订单或补充库存后尝试向最早且符合条件的用户分配抢购资格。

## 精选项目亮点

以下五条从下文的 01、02、03、05、06、07、09、10 归并而来，可用作简历中的项目亮点。数字仅为代码中的配置或分片规模，不是压测结果。

- 秒杀入口按 IP 和用户双维度限流，并使用默认有效期 **30 秒**的一次性访问令牌；下单前先过滤高频和重复凭证请求。
- 将活动时间、券状态、库存和一人一单判断放进一次 Redis Lua 执行，成功后原子预扣库存，并记录已购用户和追踪日志。
- 采用 Redis 预扣、Kafka 异步消息和消费端数据库落库的下单流程；发送失败回调、消费超时或异常时尝试回滚，并保留对账所需记录。
- 秒杀券信息使用 Caffeine + Redis 两级缓存；商户查询结合布隆过滤器、空值缓存和加锁后二次检查，券配置更新通过消息通知其他实例失效本地缓存。
- 订单表按用户 ID 选库、券 ID 选表，形成 **2 库 4 表**；结合雪花 ID 和订单路由记录支持跨分片订单标识与查询。

## 候选要点

### 01. 秒杀入口限流与访问令牌

**简历句**：围绕券抢购入口梳理按 IP 和用户维度的 Redis 限流，使用一次性短期访问令牌控制请求资格；将限流与资格校验放在库存预扣之前，减少无效请求进入核心链路。

**展开**：领令牌和抢券两个接口都调用 `RateLimitHandler`。配置默认选**令牌桶或滑动窗口二选一**，不是两个算法串行兜底；令牌桶容量、补充速率分别由窗口长度和最大次数计算。访问令牌默认 30 秒，校验成功后由 Lua 删除，它和桶里的抽象「令牌」不是同一种东西。是否支持真实 VIP 差异化阈值，应再以配置与调用链验证。

**证据**：[控制器](../citylife-core-service/src/main/java/com/citylife/controller/VoucherOrderController.java)、[限流处理器](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/java/com/citylife/execute/RedisRateLimitHandler.java)、[令牌桶 Lua](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/resources/lua/tokenBucket.lua)、[访问令牌服务](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/java/com/citylife/service/impl/SeckillAccessTokenServiceImpl.java)。

### 02. Redis Lua 预扣和一人一单

**简历句**：分析并验证秒杀 Lua 对活动时间、券状态、库存和重复购买的联合检查，成功时在 Redis 内完成库存扣减、用户集合记录和追踪日志写入。

**展开**：脚本以库存字符串键、已购用户 Set 和追踪 Hash 为输入，一次执行关键 Redis 操作，避免独立命令之间被其他请求穿插。它只能保证 Redis 内脚本执行期间的原子性，不能自动覆盖 Kafka 和 MySQL。建议准备库存为 1、两名用户并发和同一用户重复请求的实验。

**证据**：[秒杀 Lua](../citylife-core-service/src/main/resources/lua/seckillVoucher.lua)、[调用服务](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)。

### 03. Kafka 异步下单

**简历句**：梳理「Redis 预扣 -> Kafka 消息 -> 消费端落库」链路，将用户请求与数据库订单写入解耦，并通过订单查询接口区分受理和最终完成状态。

**展开**：当前 `seckillVoucher()` 调用 V2，成功预扣后发送 Kafka 消息并返回订单 ID。消费者再扣数据库库存、保存订单、路由记录和对账日志。因此「拿到订单 ID」不等于「订单已落库」。Kafka 配置有 `acks=all`、生产者重试和手动消费确认；主下单生产者的失败回调会尝试 Redis 回滚，但业务方法未等待异步 `Future`，进程在回调前宕机等窗口仍需验证。

**证据**：[订单服务](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)、[消费者](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)、[主下单生产者](../citylife-core-service/src/main/java/com/citylife/kafka/producer/SeckillVoucherProducer.java)、[Kafka 配置](../citylife-core-service/src/main/resources/application.yml)。

### 04. 消费幂等与数据库兜底

**简历句**：结合消息 UUID 的并发执行限制、用户与券维度的已有订单检查，以及数据库 `stock > 0` 条件更新，降低并发重复创建订单和超卖风险。

**展开**：消费方法上有 `@RepeatExecuteLimit`，以消息 UUID 为锁键限制并发执行；但该注解没有设置 `durationTime`，默认值是 0，切面**不会**在成功后写持久的短期成功标记。业务层另查已有正常订单，扣库时带库存大于零条件。答辩时要区分「降低并发重复风险」和「在所有故障情况下严格 exactly-once」；后者不能只靠这些代码证明。

**证据**：[订单创建方法](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)、[幂等切面](../citylife-redisson-framework/citylife-redisson-service-framework/citylife-repeat-execute-limit-framework/src/main/java/com/citylife/repeatexecutelimit/aspect/RepeatExecuteLimitAspect.java)。

### 05. 回滚与对账

**简历句**：梳理消费超时/失败后的 Redis 补偿，以及 Redis 追踪日志与数据库订单/对账日志的差异检查，形成可定位的异常处理路径。

**展开**：消费端遇到超时或异常会调用 Redis 回滚封装；回滚失败有重试与失败日志。对账服务可检查 Redis 扣减记录与 DB 订单，发现不一致时删除库存缓存、清理记录或回填追踪日志。当前只看到**手动触发对账接口**，未看到定时调度，因此不要写「已实现定时自动对账」或「所有异常自动自愈」。

**证据**：[消费者](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)、[回滚封装](../citylife-core-service/src/main/java/com/citylife/kafka/redis/RedisVoucherData.java)、[对账服务](../citylife-core-service/src/main/java/com/citylife/service/impl/ReconciliationTaskServiceImpl.java)、[对账接口](../citylife-core-service/src/main/java/com/citylife/controller/VoucherOrderController.java)。

### 06. 热点券的两级缓存

**简历句**：梳理秒杀券信息的 Caffeine 本地缓存和 Redis 缓存读取路径，结合缓存失效消息减少多实例读到旧券配置的时间窗口。

**展开**：券信息查询先查本地缓存，再查 Redis，最后才在加锁与布隆过滤器检查后回源数据库；写券配置时发布失效消息，消费者清理缓存。这里的 L1+L2 针对**秒杀券信息**，不能概括为全站所有对象都启用双层缓存。跨实例失效依赖消息到达，仍应讨论延迟与失败窗口。

**证据**：[券查询服务](../citylife-core-service/src/main/java/com/citylife/service/impl/SeckillVoucherServiceImpl.java)、[本地缓存](../citylife-core-service/src/main/java/com/citylife/cache/SeckillVoucherLocalCache.java)、[缓存失效发布器](../citylife-core-service/src/main/java/com/citylife/cache/SeckillVoucherCacheInvalidationPublisher.java)。

### 07. 商户缓存穿透与击穿处理

**简历句**：分析商户查询的布隆过滤器、空值缓存、Redis 缓存和二次检查锁组合，减少无效 ID 回源和热点缓存失效时的并发查库。

**展开**：当前 `ShopServiceImpl#queryById` 实际走 V4：先查 Redis，未命中后过布隆过滤器与空值键，再取 Redisson 锁并复查，最后查询数据库并回填。`CacheClient` 中还保留逻辑过期等教学实现，但当前商户查询入口**没有调用**逻辑过期 V3；简历不能把它说成这条查询链路的现行策略。

**证据**：[商户服务](../citylife-core-service/src/main/java/com/citylife/service/impl/ShopServiceImpl.java)、[CacheClient](../citylife-core-service/src/main/java/com/citylife/utils/CacheClient.java)。

### 08. 布隆过滤器组件

**简历句**：梳理按商户/优惠券划分的布隆过滤器配置和初始化流程，在数据库查询前快速排除明显不存在的 ID。

**展开**：布隆过滤器的「不存在」可用于拦截；「可能存在」仍需继续查询。误判概率可以配置，不是准确率 100%。若写成「我封装自动配置」，须能说明注册器、工厂、初始化和数据新增后的同步路径，并证明你确实参与了实现。

**证据**：[布隆配置](../citylife-core-service/src/main/resources/application.yml)、[组件工厂](../citylife-redisson-framework/citylife-redisson-service-framework/citylife-bloom-filter-framework/src/main/java/com/citylife/handler/BloomFilterHandlerFactory.java)、[初始化](../citylife-core-service/src/main/java/com/citylife/init/BloomFilterDataInit.java)。

### 09. 分库分表与订单路由

**简历句**：梳理 ShardingSphere-JDBC 的多库多表规则和订单路由记录，明确下单写入与按订单 ID 查询时需要的分片键。

**展开**：当前配置有两个 MySQL 数据源，多张核心表按各自字段分片；例如订单表按 `user_id` 选库、按 `voucher_id` 选表，路由表按 `order_id` 分片。没有分片键的查询可能广播到多个分片。不要笼统说「订单按订单号分片」；要指出是哪张表。

**证据**：[分片配置](../citylife-core-service/src/main/resources/shardingsphere.yaml)、[订单路由实体](../citylife-core-service/src/main/java/com/citylife/entity/VoucherOrderRouter.java)。

### 10. 雪花算法 ID

**简历句**：阅读并验证雪花 ID 生成器的时间、数据中心、节点和序列位分配，分析同毫秒高并发与时钟回拨时的行为。

**展开**：当前实现按 `41 + 5 + 5 + 12` 位组织 ID，工作节点编号通过 Redis 脚本分配；序列耗尽等待下一毫秒，时间回退会等待或报错。但 Redis 分配脚本在上限回绕，尚不能证明 K8s 重启后的动态租约回收或所有部署场景下绝对不撞号。

**证据**：[ID 生成器](../citylife-id-generator-framework/src/main/java/com/citylife/toolkit/SnowflakeIdGenerator.java)、[节点分配 Lua](../citylife-id-generator-framework/src/main/resources/lua/workAndDataCenterId.lua)。

### 11. 分布式锁与注解式并发控制

**简历句**：梳理 Redisson 注解式读写锁与业务层命令式锁的使用场景，控制券配置更新、库存加载和热点缓存回源时的并发访问。

**展开**：券查询/券更新分别使用读写锁，缓存未命中后的数据库回源另取可重入锁并二次检查。需要能解释锁键为何带券 ID、锁与数据库事务边界，以及跨 Redis/MySQL 修改时锁不能代替事务或补偿。

**证据**：[券服务](../citylife-core-service/src/main/java/com/citylife/service/impl/SeckillVoucherServiceImpl.java)、[更新服务](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)、[锁切面](../citylife-redisson-framework/citylife-redisson-service-framework/citylife-service-lock-framework/src/main/java/com/citylife/servicelock/aspect/ServiceLockAspect.java)。

### 12. 订阅、库存回流与候补分配

**简历句**：梳理券售罄后的订阅登记、按订阅时间排序的候补队列，以及取消订单或补充库存后尝试向最早的合格用户自动发券。

**展开**：订阅同时使用 Set 和 ZSet；ZSet 分数为订阅时间。取消订单会更新订单状态、恢复 DB 库存、处理 Redis 状态，再尝试查找最早且尚未购买的订阅用户，经过用户等级和 Lua 检查后发 Kafka 消息。属于「尝试自动分配」，并非在所有异常下保证公平交付。

**证据**：[订阅服务](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)、[取消与候补](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)。

### 13. 开抢前提醒与 Top 买家

**简历句**：梳理 Redisson 延迟队列触发开抢提醒，利用 Redis Set/ZSet 选择用户并做通知去重；消费成功后按店铺和日期累计购买次数，为运营筛选提供数据。

**展开**：延迟消息用于开抢提醒；提醒消费者从用户等级和近日期 Top 买家等集合选人，用 Redis 去重键控频。当前默认短信/App 开关为 `false`，相关路径主要记录日志，不应写成「已对接真实短信平台」。Top 买家目前累加的是**订单次数**，不是消费金额；也未找到订单超时未支付自动关闭链路。

**证据**：[提醒调度](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)、[提醒消费](../citylife-core-service/src/main/java/com/citylife/delay/consumer/ConsumerDelayedVoucherReminder.java)、[订单消费者](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)。

### 14. 监控埋点与可运行部署

**简历句**：梳理 Micrometer 计数指标与 Prometheus 暴露端点，并使用 Docker Compose 启动前端、后端、MySQL、Redis、Kafka，完成本地链路验证。

**展开**：应用暴露 `prometheus/health/info`，限流、回滚、缓存失效等路径有计数指标；这不等于已完成 P95/P99 压测画像或告警闭环。Docker Compose 一键启动是当前工作区可见的部署能力。此条尤其适合写你真实做过的环境整理和验证，但仍要填入测试记录。

## 暂时不要写进简历的强断言

- **「令牌桶 + 滑动窗口串行兜底」**：当前代码是配置选择其中之一。
- **「主下单消息有指数退避 + DLQ + 本地消息表兜底」**：当前主下单有 Kafka 配置重试和失败回调尝试回滚；专门的指数退避/DLQ 在**缓存失效消息**链路，未找到主下单 Outbox。
- **「定时自动对账、自愈所有 Redis/MQ 故障」**：有对账方法和手动接口，未找到定时调用；无法承诺所有故障自动恢复。
- **「订单超时未支付自动关闭」**：找到的是开抢提醒延迟队列，未找到自动关单消费者。
- **「K8s Worker ID 动态注册与回收，保证绝不重复」**：当前 Redis Lua 自增分配并回绕，不是带租约的注册/回收。
- **「全站双层缓存、逻辑过期异步重建」**：券信息确有 L1+L2；商户查询当前走 V4 锁与 Redis，逻辑过期 V3 不是现行路径。
- **「消费金额 Top 买家、真实短信触达、百万并发、P99 显著改善」**：当前代码或实测记录不足以支持这些说法。
