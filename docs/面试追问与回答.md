# CityLife 面试追问与回答

> 对应[简历候选要点](简历候选要点.md)的 14 条内容。每题分为「理解版」和「30-60 秒面试简答版」。以下回答描述**当前代码**，不是你的个人贡献声明；回答前先确认你确实做过什么。面试中遇到未实现的能力，应说明现状、风险和改进方案，不能把方案说成已上线结果。

## 01. 为什么已经有限流，还要签发一次性访问令牌？

**理解版**：两者控制的是不同问题。令牌桶/滑动窗口控制某 IP 或用户在一段时间内的请求频率；访问令牌证明特定用户针对特定券取得了一次短期调用资格。控制器在领令牌接口和下单接口都先限流；领令牌时生成 UUID 并按「券 ID + 用户 ID」存入 Redis，默认 30 秒；下单时 Lua 比较值，相同就删除，让同一枚令牌不能重复使用。即使拿到令牌，也仍要经过活动时间、用户等级、库存和一人一单检查。令牌不能代替登录鉴权，也不能保证最终下单成功。

**30-60 秒面试简答版**：我把入口分成速率和资格两层：Redis 限流控制 IP/用户请求频率，短期一次性访问令牌控制单次抢券调用。请求真正扣库存前，还要经过业务资格与 Lua 校验。令牌桶的令牌是内部额度，访问令牌是客户端提交的凭证，不能混为一谈。

**代码**：[控制器](../citylife-core-service/src/main/java/com/citylife/controller/VoucherOrderController.java)、[访问令牌服务](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/java/com/citylife/service/impl/SeckillAccessTokenServiceImpl.java)。

## 02. 令牌桶和滑动窗口在这里是什么关系？

**理解版**：当前配置 `enableSlidingWindow=false`，`RedisRateLimitHandler` 默认执行令牌桶 Lua；设为 `true` 才执行滑动窗口 Lua，所以它们是可切换的两种策略，**不是先令牌桶再滑动窗口兜底**。令牌桶在 Redis Hash 记剩余令牌和上次时间，用「经过时间 × 补充速率」补令牌，适合允许一定突发量。滑动窗口用 ZSet 保存请求时间，先清掉窗口外记录，再用集合数量判断是否超限。两种脚本都分别检查 IP 和用户；要解释默认容量与补充速率，还需看配置覆盖情况。

**30-60 秒面试简答版**：项目用配置在令牌桶和滑动窗口之间切换。令牌桶允许容量内的瞬时突发，并按时间连续补充；滑动窗口更直接地限制最近一段时间的请求数。当前默认选令牌桶，两个算法不是串行执行。

**代码**：[限流处理器](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/java/com/citylife/execute/RedisRateLimitHandler.java)、[令牌桶 Lua](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/resources/lua/tokenBucket.lua)、[滑动窗口 Lua](../citylife-redis-tool-framework/citylife-redis-rate-limit-framework/src/main/resources/lua/rateLimitSliding.lua)。

## 03. Lua 为什么能避免秒杀超卖？能保证整个订单事务吗？

**理解版**：如果库存为 1，两个请求分别「GET 库存 -> 判断 -> DECR」，两者可能都先读到 1。当前脚本在 Redis 内一次执行时间、状态、库存和重复购买检查，成功时扣减库存、加入已购用户 Set、写追踪 Hash；另一个请求不会插到检查与扣减之间，所以能避免这段 Redis 操作的竞态。它**不能**把 Kafka 发送、MySQL 库存更新和订单插入纳入同一原子事务。Lua 运行时如果中途报错，Redis 也不会像数据库事务一样自动回滚此前写入；仍需错误处理、补偿和对账。

**30-60 秒面试简答版**：Lua 解决的是 Redis 内多步校验和扣减被并发请求穿插的问题。脚本成功后，库存和已购集合一起变化。但这只是 Redis 局部原子性，Kafka 投递与 MySQL 落库仍是另一段链路，因此项目还需要失败回滚和对账。

**代码**：[秒杀 Lua](../citylife-core-service/src/main/resources/lua/seckillVoucher.lua)。

## 04. 接口返回订单 ID，订单就一定成功了吗？

**理解版**：不一定。`seckillVoucher()` 当前调用 V2：Redis 脚本成功后构造消息，调用 `sendPayload` 并返回生成的订单 ID。`sendPayload` 返回 `CompletableFuture`，业务方法没有等待确认；主下单生产者在异步失败回调里尝试 Redis 回滚。之后消费者才执行数据库条件扣库存、插入订单和对账日志。因此订单 ID 是一次请求的标识，不是 Kafka/数据库提交凭据。客户端应通过订单查询接口确认最终结果；若要更强保证，需对回调前进程宕机窗口补足持久化待投递记录（如 Outbox）和故障验证。

**30-60 秒面试简答版**：不能。接口先在 Redis 预扣并异步发送 Kafka，然后返回 ID；消费者之后才落库。生产者失败回调会尝试回滚，但业务请求不等待 Future，因此 ID 只是受理标识；回调前宕机等窗口仍需额外补偿和验证。

**代码**：[订单服务](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)、[主下单生产者](../citylife-core-service/src/main/java/com/citylife/kafka/producer/SeckillVoucherProducer.java)、[生产者抽象](../citylife-mq-framework/citylife-mq-producer-framework/src/main/java/com/citylife/AbstractProducerHandler.java)。

## 05. Kafka 消息重复投递时，为什么不一定产生重复订单？

**理解版**：Kafka 消费在异常/重试时可能重复。消费方法按消息 UUID 加 `@RepeatExecuteLimit`，用本地/分布式锁限制**并发执行**；但注解 `durationTime` 默认为 0，当前调用没有覆盖，所以成功后不会保存去重标记，顺序重放不能只靠该注解挡住。业务层按用户 ID 和券 ID 查询已有正常订单；扣数据库库存使用 `stock > 0` 条件更新。查询与插入并非天然原子，对所有并发/重放情形要想更强保证，还需检查数据库唯一约束和实际并发测试；不能直接宣称 exactly-once。

**30-60 秒面试简答版**：消费端用消息 UUID 锁限制并发执行，再查「用户 + 券」是否已有订单，并用 `stock > 0` 条件更新兜住库存。这里注解默认不保存成功标记，所以它不是完整去重；我不会宣称 exactly-once，还要核对数据库约束与重放时序。

**代码**：[订单创建方法](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)、[幂等切面](../citylife-redisson-framework/citylife-redisson-service-framework/citylife-repeat-execute-limit-framework/src/main/java/com/citylife/repeatexecutelimit/aspect/RepeatExecuteLimitAspect.java)。

## 06. Redis 已扣库存，但消息没发出去或消费者落库失败，怎么办？

**理解版**：先区分故障位置。消费者已收到但处理超时/失败时，消费者会调用回滚封装；回滚 Lua 删除 Redis 库存缓存、按条件从已购集合移除用户、写恢复追踪日志，库存之后可按数据库值重建。若回滚失败，封装做有限重试并记录失败日志。**消息发送失败并触发回调**时，`SeckillVoucherProducer#afterSendFailure` 也会尝试回滚；但主订单发送使用异步 Future，未发现主订单 Outbox，进程在回调前宕机等情况仍可能留下不一致。完善方式可以是可靠本地事件记录、发送确认、可重试投递和对账扫描，但应作为改进方案陈述。

**30-60 秒面试简答版**：消费失败和生产者发送失败回调都尝试 Redis 回滚；回滚是删库存缓存后从数据库重建，并非简单 `INCR`。但请求没有等待 Kafka 确认，也没找到 Outbox，所以回调前宕机仍是风险窗口，我会用持久化待投递记录和对账补齐。

**代码**：[消费者](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)、[主下单生产者](../citylife-core-service/src/main/java/com/citylife/kafka/producer/SeckillVoucherProducer.java)、[回滚 Lua](../citylife-core-service/src/main/resources/lua/seckillVoucherRollBack.lua)、[回滚封装](../citylife-core-service/src/main/java/com/citylife/kafka/redis/RedisVoucherData.java)。

## 07. 这个项目的对账是怎样工作的？是否定时自动执行？

**理解版**：Lua 成功时向 Redis Hash 写扣减追踪日志；消费者落库时写数据库订单和对账日志。`ReconciliationTaskServiceImpl` 按券加载 Redis 追踪记录与待处理订单，发现 Redis 扣减记录但缺数据库对应记录时，删除 Redis 库存缓存、清理相关用户标记；对 DB 有而 Redis 追踪缺失的情形，回填追踪，并根据日志情况标记订单状态。代码能证明**有对账方法和手动触发接口**，但在当前服务中未找到 `@Scheduled` 或其他周期调度入口，所以不能说它已经定时自动运行，更不能说它保证处理所有主从切换/宕机场景。

**30-60 秒面试简答版**：对账把 Redis 预扣追踪和数据库订单/日志相互核对，发现差异后删库存缓存重建、清理用户状态或回填追踪。当前项目有对账实现与手动接口；是否定时执行不能想当然，我核对代码后没有找到调度入口，因此会把定时化列为后续完善项。

**代码**：[对账服务](../citylife-core-service/src/main/java/com/citylife/service/impl/ReconciliationTaskServiceImpl.java)、[对账接口](../citylife-core-service/src/main/java/com/citylife/controller/VoucherOrderController.java)。

## 08. L1+L2 缓存具体缓存了什么？更新后如何失效？

**理解版**：当前明确采用两级缓存的是**秒杀券信息**：先查 Caffeine 本地缓存，未命中查 Redis，再未命中才在布隆检查、空值判断、加锁后二次检查并查数据库。券配置更新会先清本实例本地缓存和 Redis 相关键，再发 Kafka 缓存失效消息，其他实例消费后清理本地缓存。这样减少热读访问 Redis 的次数，但跨实例消息存在传递延迟或失败窗口，不能说所有实例即时强一致；应靠 TTL、重试/DLQ 和实际故障测试评估。

**30-60 秒面试简答版**：项目的两级缓存主要落在秒杀券信息：Caffeine 作为 L1、Redis 作为 L2，数据库是最后回源。更新时清本地和 Redis，并广播失效消息到其他实例。它降低读路径开销，但跨实例更新仍是最终收敛，不是瞬时强一致。

**代码**：[券查询](../citylife-core-service/src/main/java/com/citylife/service/impl/SeckillVoucherServiceImpl.java)、[失效发布](../citylife-core-service/src/main/java/com/citylife/cache/SeckillVoucherCacheInvalidationPublisher.java)。

## 09. 缓存穿透和缓存击穿有什么区别？当前商户查询怎么处理？

**理解版**：穿透是查询本就不存在的数据，缓存不命中后反复访问数据库；击穿是某个热点数据的缓存失效，大量请求同时回源。当前商户查询 `queryById()` 调用 V4：Redis 命中直接返回；未命中用布隆过滤器先排除明显无效 ID，再检查空值键；还未解决则取 Redisson 锁，锁内再次查缓存/空值键，只让持锁者回源数据库并写缓存。`CacheClient` 里有逻辑过期实验代码，但 V3 并非当前商户入口；不要把「逻辑过期 + 异步重建」说成现行链路。

**30-60 秒面试简答版**：穿透是无效 ID 一直查库，击穿是热点键失效后请求一起查库。当前商户入口用布隆过滤器和空值缓存挡穿透，用 Redisson 锁加二次检查控制击穿回源。仓库也保留逻辑过期实现，但不是这条接口当前调用的版本。

**代码**：[商户服务](../citylife-core-service/src/main/java/com/citylife/service/impl/ShopServiceImpl.java)。

## 10. 布隆过滤器说“存在”，为什么还要访问 Redis/数据库？

**理解版**：布隆过滤器是概率型集合。它说「不存在」时，可以快速拒绝；它说「可能存在」时，可能是误判，仍需以 Redis 或数据库为准。项目分别配置商户、优惠券过滤器，并在启动/新增等路径维护数据。面试还应说明误判率与空间成本权衡，以及漏加数据会导致**假阴性**，因此初始化和增量同步比接口调用本身同样重要。不能说它单独保证数据存在或一定防住全部穿透。

**30-60 秒面试简答版**：布隆过滤器只能可靠地排除明显不存在的 ID，命中代表「可能有」，仍要查缓存或数据库。它以空间换查询速度，配置中有误判概率；业务上最重要的是保证合法 ID 被及时加入，否则会错误拦截真实数据。

**代码**：[过滤器工厂](../citylife-redisson-framework/citylife-redisson-service-framework/citylife-bloom-filter-framework/src/main/java/com/citylife/handler/BloomFilterHandlerFactory.java)、[初始化](../citylife-core-service/src/main/java/com/citylife/init/BloomFilterDataInit.java)。

## 11. 订单为什么还需要路由表？订单按什么字段分片？

**理解版**：分片键要按**具体表**说。`tb_voucher_order` 在配置中按 `user_id` 选库、按 `voucher_id` 选表；按订单 ID 查询时，只有 `order_id` 往往不足以直接定位其订单分片。项目额外保存 `tb_voucher_order_router`，它按 `order_id` 路由，记录订单对应的用户和券，设计上可借此取回订单表所需的分片键。当前按订单 ID 查询接口先查 Redis，再查询路由表来确认订单 ID，不能声称所有查询都已经「先路由再查订单」。没有合适分片条件的查询可能广播，影响性能。

**30-60 秒面试简答版**：分片规则不能一句「按订单号」带过。实际订单表按用户选库、按券选表；路由表按订单号分片，保存用户和券这两个业务键。它提供从订单号找分片键的可能，但当前接口主要用路由记录确认订单存在，不能夸大为所有查询都已按路由表优化。

**代码**：[ShardingSphere 配置](../citylife-core-service/src/main/resources/shardingsphere.yaml)、[落库逻辑](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)。

## 12. 雪花 ID 如何避免重复？时钟回拨和节点重启怎么办？

**理解版**：经典思路是用不同节点编号分隔不同实例，用同一毫秒的自增序号分隔一个实例内的多个请求。当前实现有 41 位时间、5 位数据中心、5 位节点、12 位序号；同毫秒序号用尽后等下一毫秒。检测到时间回拨时，小幅回拨尝试等待，大幅回拨抛异常。节点编号由 Redis Lua 分配，但脚本达到上限后会回绕，未看到带租约的注册/回收机制；若不同活跃实例取得同一编号，或 Redis 状态丢失，仍有碰撞风险。准确说法是「节点编号唯一且时钟满足约束时，位组合可以保证生成的 ID 不重复」；当前部署是否一直满足前提，需要验证。

**30-60 秒面试简答版**：雪花 ID 用时间、节点编号和毫秒内序号组合。当前实现能处理序号耗尽和一定程度的时钟回拨，但唯一性的前提是活跃节点编号不重复。Redis 分配脚本会回绕，所以我不会宣称它已经解决所有 K8s 重启与多实例编号冲突；需要增加租约或稳定节点身份并压测验证。

**代码**：[雪花 ID](../citylife-id-generator-framework/src/main/java/com/citylife/toolkit/SnowflakeIdGenerator.java)、[节点分配脚本](../citylife-id-generator-framework/src/main/resources/lua/workAndDataCenterId.lua)。

## 13. 有了分布式锁，为什么还要数据库事务和业务条件？

**理解版**：锁限制同一锁键下同时执行的线程或实例，但不负责数据库事务回滚，也不自动管理 Redis/Kafka 副作用。项目更新券时按券 ID 用注解式写锁，查券用读锁；商户/券缓存回源则取可重入锁并二次检查。数据库扣库存还要 `stock > 0` 条件，消费落库方法标了 `@Transactional`。但订单/券可能落到不同分片；跨库原子提交还取决于 ShardingSphere 和事务配置，当前未见明确 XA 配置，不应直接保证。对于「数据库已回滚但 Redis 已更新」的跨系统场景，锁本身无能为力，必须设计缓存失效或补偿路径。

**30-60 秒面试简答版**：锁控制同一业务键的并发顺序，`stock > 0` 条件更新守住库存，事务管理数据库操作。跨多个分片是否原子还要看事务模式；Redis 和 Kafka 也不会随 MySQL 自动回滚，所以必须单独考虑补偿与对账。

**代码**：[券更新](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)、[订单落库](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)。

## 14. 售罄订阅怎样保证“先来先得”？

**理解版**：订阅用户被存到 Set 和按订阅时间计分的 ZSet。取消订单或补充库存后，代码从 ZSet 里找时间最早的候选者，跳过取消用户和已购买者，再校验用户等级，调用同一套秒杀 Lua 预扣并发消息。这个顺序在数据结构层面体现「按订阅时间优先」，但最终成功还受库存、资格、消息投递和并发影响；目前不能宣称任何故障下都严格公平。通知还要区分「自动发券下单」与「只是告知用户有券」两个动作。

**30-60 秒面试简答版**：订阅 ZSet 用时间做分数，补库存或取消订单后先找最早且未购买、符合等级的用户，再通过 Lua 扣库存和 Kafka 异步下单。它是一个按时间优先的候补策略，但并发和消息失败仍可能影响最终交付，需要状态记录与补偿验证。

**代码**：[订阅](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherServiceImpl.java)、[候补分配](../citylife-core-service/src/main/java/com/citylife/service/impl/VoucherOrderServiceImpl.java)。

## 15. 延迟队列、Top 买家和真实通知分别做到哪一步？

**理解版**：券服务在开抢前计算延迟时间，将提醒消息放入 Redisson 延迟队列；消费者从用户等级和历史 Top 买家等 Redis 集合选出目标用户，用 Redis 键进行去重控频。订单成功后，消费者把店铺当日用户的 ZSet 分数加 1，代表购买**次数**，取消订单时减 1。当前提醒的短信/App 开关默认关闭，相关代码主要写日志，不能说已对接真实消息平台，也不能说 Top 买家按消费金额排序。搜索项目未见订单超时未支付自动关单的完整延迟消费者。

**30-60 秒面试简答版**：当前延迟队列用于开抢前提醒；Top 买家通过 Redis ZSet 按购买次数累计，供选人使用。短信/App 默认没有真实发送，因此我会把它描述成通知链路的内部实现，不声称已完成外部触达或自动关单。

**代码**：[延迟提醒](../citylife-core-service/src/main/java/com/citylife/delay/consumer/ConsumerDelayedVoucherReminder.java)、[订单消费者](../citylife-core-service/src/main/java/com/citylife/kafka/consumer/SeckillVoucherConsumer.java)。

## 16. 你如何证明“高并发稳定”和“性能改善”？

**理解版**：仅有架构图、Prometheus 端点和计数器，不足以证明容量与效果。应固定环境和数据规模，设计基线与改进版本，给出压测工具、并发用户数、持续时间、QPS、成功率、P95/P99、Redis/DB/Kafka 资源占用与积压；重复多次并记录误差。还要做故障注入，如 Kafka 不可用、Redis 重启、消费延迟、重复消息，对比 Redis 库存、数据库库存和订单数量。当前工作区能看到部分 Micrometer 计数和 Prometheus 暴露配置，但未发现可引用的正式压测报告，所以不能填写“百万并发”“提升 XX%”。

**30-60 秒面试简答版**：我不会仅凭用了 Redis/Kafka 就说能抗高并发。要在固定环境下对比 QPS、成功率、P95/P99 和消息积压，再通过故障注入核对订单与库存。这个工作区有监控入口，但没有足够的压测结果支撑具体性能数字；简历中的数字必须来自实测。

## 17. Docker 一键启动代表什么？不代表什么？

**理解版**：`docker compose up -d --build` 可以在本地编排前端、后端和依赖服务，降低复现环境的成本；通过 Compose 状态、健康检查、接口响应和浏览器操作确认链路可用。它不自动证明应用已经具备生产级高可用、数据备份、安全配置或真实并发容量。简历可写「完成本地容器化部署与验证」，不要据此写「生产部署落地」。

**30-60 秒面试简答版**：Docker Compose 的价值是把环境和启动步骤固化，让他人能复现本地业务链路。我会验证服务健康、页面和关键接口，但不会把本地一键启动等同于生产高可用部署。
